# 収益改善のための検証・取引制御 機能設計

作成日: 2026-09-12。対象: Noctas のペーパートレード。状態: 実装前の設計案。

## 1. 目的と範囲

目的は、コスト控除後の利益と資産減少リスクを同じ条件で評価し、根拠のある戦略だけを段階的に稼働させること。収益改善そのものは未検証であり、本設計の完成条件は利益の保証ではなく、再現性・比較可能性・取引制御の正確さとする。

実装順は「検証の正確性 → 長期検証 → コスト判定 → リスク配分 → 相場別戦略・AI比較」。実注文API、信用取引、モデル変更の自動適用は対象外。

既存の Blueprint、戦略別SL/TP/トレーリング、日次損失停止、連敗停止、AI利用料表示を拡張する。既存戦略の売買条件を移行時に黙って変更しない。

## 2. ユーザーの操作

1. Blueprintを保存すると、グラフ・時間足・出口・投入額設定を固定した戦略バージョンが作られる。
2. 「検証」で期間、初期資金、取引コスト、執行方式を選び、通常バックテストを実行する。
3. 「期間を分けて検証」で学習期間と評価期間を設定し、ウォークフォワードを実行する。
4. 資産推移、純損益、最大ドローダウン、取引数、比較対象との差、制約による見送り理由を見る。
5. 候補を固定し、未使用の最終評価期間を一度評価する。結果閲覧後に変更した候補は、同じ期間を未使用として扱わない。
6. 「ペーパーで試す」で採用するバージョンとリスク設定を表示し、ユーザーが適用する。
7. 稼働後は予想と実績の差を確認し、変更は新しいバージョンとして再検証する。

状態は Draft → Tested → Candidate → ForwardTesting → Paused。取引数不足は InsufficientData として別表示し、負け戦略と混同しない。これらは検証状態であり、既存 isActive による稼働状態とは別に管理する。過去データの成績だけで自動稼働させない。

## 3. 機能A: 稼働と検証の共通売買エンジン（P0）

### 判断と執行

- 新規戦略の標準は `closed_bar_next_tick`。確定した足で一度判断し、その情報が利用可能になった後の最初の取引可能価格で執行する。
- OHLCバックテストでは次足始値をその代理価格とする。稼働時の次tickとは完全一致しないため、結果に執行モデルを表示する。
- 既存戦略は `legacy_intrabar` として保持する。終値データのみでは稼働再現不可と表示し、厳格な評価済み認定の対象外にする。移行は設定変更として明示する。
- SL/TP/トレーリングの保護決済は足確定を待たず、到着価格で評価する。エントリーのクールダウンで保護決済を止めない。
- buy/sell同時成立時は既存どおりsell優先。建玉制約・残高・クールダウン・停止判定を共通の関数で処理する。
- シグナルの一意キーは strategyVersionId + pair + barCloseAt + action。再起動・再送・並行処理でも注文を重複させない。

### 足内価格とストップ

- OHLCしかない期間は、始値→安値→高値→終値を標準の近似経路として採用する。高値を先に見てから過去の安値へトレーリングを遡及適用しない。
- 始値→高値→安値→終値も感応度シナリオとして評価し、同一足内で結論が変わる取引数と損益差を表示する。一方の経路を常に最悪と断定しない。
- 始値が損切りラインを下回っている場合は、ラインではなく始値に売却コストを適用する。
- 最終足で生じた新規注文は約定させず、次の価格がないため未執行と記録する。

### 資産と損益

- `liquidationEquity = cash + Σ(positionAmount × executableSellPrice − estimatedExitFee)`。
- 入口手数料は購入時にcashから引く。スリッページは約定価格に含め、別途二重控除しない。
- `netEconomicEquity = liquidationEquity − cumulativeAiOperatingCost`。AI費用は仮想JPY残高からは引かず、経済損益にだけ反映する。
- 最大DDは各評価時点の資産ピークからの下落額と率。通常資産とAI費用控除後資産の両方を保持する。
- 期間末は未決済ポジションを売却想定価格で評価し、実現損益・未実現損益・末尾建玉を別表示する。強制決済シナリオは別モードとする。
- バー単位DDは足内の最大損失を保証しない。評価粒度を表示する。

### 受入条件

- 同じ価格イベント・設定・初期状態を入力したペーパー経路と検証経路で、注文理由、数量、手数料、残高が一致する。
- 含み損だけが増えるケースでもDDが増加する。売却時に含み損が実現損へ移る際、損失を二重計上しない。
- ギャップ下落、同足SL/TP成立、残高不足、再起動後の重複シグナルを固定データで検証する。

## 4. 機能B: 長期間のウォークフォワード（P1）

### データ・計算

- HistoricalCandleを起点に、期間指定取得と不足分の収集を行う。取引所で取得可能な範囲を確認し、取れない期間を捏造・無言短縮しない。
- 標準の試験案は学習60日・評価14日・14日ずつ移動、最終評価30日。これは利益を保証する最適値ではなくUIの初期案であり、実際のデータ量と取引頻度に合わせて変更する。
- 少なくとも3評価窓を作れない場合は必要期間を表示する。計算都合で足数へ短縮しない。
- データのペア・期間・欠損・収集日時・ハッシュを保存する。修正や追加で過去の実行結果を書き換えない。
- 指標を差分更新または事前計算し、worker threadで実行する。HTTPは202とjobIdを返し、進捗とキャンセルを提供する。
- 同時実行は初期設定1件。キュー、実行時間上限、メモリ上限を設ける。アプリ終了後は中断状態を保存し、再実行を案内する。

### 学習と評価の境界

- ウォームアップ足は評価開始前から供給し、損益集計と発注は評価開始後に限定する。
- 学習・パラメータ選択では評価期間の価格と成績を参照しない。保有期間が境界をまたぐラベルを学習に使わない。
- 学習候補の比較時は未決済建玉も評価する。
- OOSは共有口座で連続再生する。次窓で設定が変わっても既存建玉の出口設定は建玉時の値を維持し、新規建玉から新設定を使う。窓ごとに資金を初期化した結果を合算しない。
- 最終推奨設定は事前に定義した学習側の選定規則で決める。OOSの利益を同点決着に使わない。

### 候補選定

- 学習内の時系列分割で、コスト控除後の平均取引損益、DD、取引数、近隣パラメータの安定性を比較する。
- 取引不足時に制約を外して最高利益候補を推薦する処理は廃止し、判定保留にする。
- 試した候補数と設定履歴を保存する。最終評価期間の使用履歴はユーザー単位の研究履歴として保持する。
- 単一のPF閾値だけで合格にしない。最低取引数、DD上限、コスト悪化時の許容結果はValidationPolicyに明示する。閾値は統計的保証と表現しない。
- ブロック単位の再標本化で期待値の不確実性を推定する。取引が少ない場合は区間推定自体を参考値または算出不能として表示する。

比較対象は現金保持、同額の買い持ち、同じ売買条件でフィルターを外した戦略。初期資金・期間・コストをそろえる。

### 受入条件

- 評価期間のデータを変更しても、直前の学習窓から選ばれる設定が変わらない。
- ウォームアップ中に取引しない。窓の切替で現金・建玉・損益が消えない。
- 合意した基準PCで90日1分足・既定48候補を測定し、実行中もtickerの処理遅延が通常時比で大幅に悪化しないことを確認する。所要時間とメモリの数値目標は初回ベンチマーク後に固定する。

## 5. 機能C: コストを考慮したエントリー（P1）

### 価格モデル

- CostProfileをペア・適用期間・売買方式ごとに保存する。手数料、価格基準、スプレッド、追加スリッページを区別する。
- bid/askがある場合は買いask・売りbidを基準にする。このときスプレッドをもう一度控除しない。
- 過去の板情報がない場合は固定コスト仮定と表示し、標準・コスト1.5倍・2倍で比較する。
- 古い相場情報や価格欠損では新規買いを見送る。保護決済は利用可能な価格で継続し、欠損中に架空の約定を作らない。

### 判定

- 第一段階は計測のみ。各シグナルで推定コストと結果を記録し、既存の売買は変えない。
- 次にスプレッド上限とデータ鮮度を有効化する。
- 学習データが十分な戦略では、同じ出口ルールの過去取引から得たコスト前期待収益の保守的推定値が、現在の往復コスト + safetyMarginを超えるときだけ新規買いを許可する。
- 推定値はバージョン付きで固定し、バックテストでもその時点で利用可能だったものだけを使う。AIのconfidenceやATRを利益予測に代用しない。
- 純損益から推定したモデルを使う場合は、学習時コストとの差分だけを調整し、往復コストを二重控除しない。
- データ不足時は厳格モードでは見送り、計測モードでは従来条件で執行して「期待値未検証」と記録する。
- 決済にこのゲートを適用しない。

ログはEXECUTED / COST_TOO_HIGH / EDGE_INSUFFICIENT / INSUFFICIENT_DATA / STALE_MARKET / RISK_LIMIT / COOLDOWN等の理由コードと数値を保存する。見送ったシグナルの仮想結果は別口座の比較実験で評価し、実現利益に加えない。

## 6. 機能D: 損失予算による資金配分（P2）

- positionSizingModeは既存fixed_jpyと新規risk_budgetを提供する。
- risk_budgetでは `投入額上限 = 資産額 × 許容損失率 ÷ (損切り率 + 往復コスト率 + ギャップ余裕率)` を初期近似とし、具体的な約定価格で再検算して切り下げる。
- 戦略上限・全体投入上限・利用可能JPY・最小注文単位のすべてを満たす数量にする。損切り不能・ゼロ幅の場合は新規買いを拒否する。
- 全建玉の損切り想定損失を合計して制限する。損切りは価格飛びを防げないため、この値を最大損失保証と表示しない。
- ペア別と関連銘柄グループ別の投入上限を設定する。将来の相関推定導入までは手動グループとする。
- 日初資産からの含み損込み下落率と、累積ピークからのDDで新規買いを停止する。全決済は別機能として扱い、自動的に併発させない。
- 複数戦略の同時注文でも予算を超えないよう、注文予約・残高・建玉記録をトランザクションで更新する。

## 7. 機能E: 相場別戦略とAI貢献度（P3）

### 相場別戦略

- ノード追加: ATR、ADX、上位時間足参照、レンジ幅。上位時間足は確定済みの足だけ参照する。
- 相場状態はtrend / range / stressed / unknown。閾値付近の頻繁な切替を抑える確認本数と復帰条件を設ける。
- 初期用途は新規買いの許可条件。稼働中の建玉のSL/TPを相場状態に合わせて無断変更しない。
- ATR損切りは建玉時点のATRで固定し、トレーリングは別設定として管理する。
- フィルターなしと同条件で比較し、改善したものだけユーザーが採用する。

### AI比較

- AiDecisionLogを拡張し、入力スナップショット、判断対象時間足、入力締切時刻、応答受信時刻、モデル、プロンプトバージョン、実際の推定費用を保存する。
- 過去再生では応答受信時刻以降にのみ判断を利用する。AI呼出し開始時刻へ遡って利用しない。判断TTLと消費済み状態も再現する。
- 古いログで時刻・入力の再現に必要な情報がない期間はAI比較不可とする。将来情報を知り得る現在のモデルで過去判断を生成して正式OOSに混ぜない。
- ルールのみ / ルール+AIを独立した仮想口座で同時に走らせ、資金競合させない。
- 判断生成費は、対象ペアでその判断を利用する稼働戦略に等分配賦するのを初期規則とし、実験比較ではAI側に全額計上する。全体集計では費用を重複計上しない。
- AIによる見送り改善、純利益差、DD差、取引数差を表示する。confidenceは確率とみなさず、定義した成果ラベルごとに実績を集計する。

## 8. 画面仕様

### 戦略詳細「検証」タブ

- 上部: 対象バージョン、期間、時間足、初期資金、コスト条件、評価状態。
- 主指標: 決済想定純損益、AI費用控除後純損益、最大DD額・率、取引数、平均取引損益。
- 資産推移: 戦略、現金、買い持ち。実現損益だけの線は補助表示。
- 詳細: 各評価期間、コスト感応度、足内経路感応度、末尾建玉、欠損、見送り理由。
- PFは損失ゼロの場合に無限大で優秀と表示せず「算出不能（損失取引なし）」とする。
- 実行中は進捗・待機件数・キャンセルを表示し、画面を離れて戻っても結果を確認できる。

### 稼働設定

- 既存SL/TP設定に判断タイミング、コスト制御、投入額方式を追加。
- risk_budgetは注文予定額と損切り想定損失を例示する。
- 適用前に旧設定との差を表示。変更後は新バージョンとなり、古い検証結果を新設定の評価として表示しない。

### PnL画面

- 戦略バージョンごとの実績、コスト、AI費用、資産下落率、見送り件数を表示。
- 「利益の減少要因」を価格損益、手数料、推定執行コスト、AI費用に分解する。推定執行コストは分析内訳であり損益から二重控除しない。
- 期待と実績の差が出ても自動再最適化せず、再検証への導線を提供する。

## 9. 保存モデルとAPI

追加モデル:

| モデル | 主な内容 |
| --- | --- |
| StrategyVersion | strategyId、version、graph、解決済みリスク設定、判断方式、内容hash、作成日時 |
| DatasetSnapshot | 対象ペア・期間、データhash、欠損概要、元データ識別子 |
| CostProfile | ペア、適用期間、手数料、価格基準、スリッページ仮定、version |
| ValidationPolicy | 学習・評価窓、候補選定規則、取引数・DD条件、version |
| ValidationRun | 戦略・データ・コスト・規則のID、エンジンversion、seed、status、進捗、結果概要、エラー |
| ValidationWindow | Run内の窓、学習/評価境界、選択設定、指標 |
| ValidationArtifact | 資産曲線・取引明細の保存先とhash。大量JSONをStrategyに埋め込まない |
| EntryDecisionLog | strategyVersionId、時刻、一意キー、可否、理由、コスト、期待値モデルID、リスク予算 |
| EdgeEstimate | 学習締切、対象条件、サンプル数、推定値・区間、出口ルールhash |
| HoldoutUsage | 評価期間、閲覧日時、実験系列、使用した候補 |

Position/Trade/BotSignalLogにstrategyVersionIdを追加。既存行は不明な履歴を推測せずnullを許す。新規建玉にはグローバル既定値を解決した出口設定とコスト参照を保存する。AiDecisionLogは前節の時刻・入力情報を追加し、旧行は再現性不足を明示する。

追加API案:

- `POST /api/validation-runs`: 保存済み戦略versionまたは保存前の内容snapshot、データ期間、初期資金、profile/policy、modeを受け、202 + runId。
- `GET /api/validation-runs/:id`: 状態、進捗、結果概要。
- `GET /api/validation-runs/:id/trades` と `/equity`: ページングした明細。
- `POST /api/validation-runs/:id/cancel`: 冪等なキャンセル。
- `GET /api/strategies/:id/versions`: バージョン履歴。
- `POST /api/strategies/:id/adopt-validation`: runIdと想定する現在versionを指定。変更競合は409。稼働設定を適用し、新versionを作成する。
- `GET /api/entry-decisions`: 戦略・期間・理由別のログ。

既存backtest/walk-forward APIは移行期間中維持する。新しい画面は非同期APIを使用し、旧結果を新指標の意味に上書きしない。WSへvalidation_progressイベントを追加し、GETでも復帰可能にする。

## 10. 実装単位とリリース順

1. **PR1: 損益評価の正確化** — 末尾建玉評価、資産/DD、費用の二重計上防止、指標の新型と画面表示。
2. **PR2: 判断・執行の統一** — 確定足方式、価格イベント再生、出口経路、ギャップ、資金制約、停止処理、戦略version。
3. **PR3: 非同期検証** — worker、差分指標、job保存、キャンセル、データsnapshot。
4. **PR4: ウォークフォワード刷新** — カレンダー窓、ウォームアップ、連続口座、選定規則、最終評価履歴。
5. **PR5: コスト計測とゲート** — まず計測、その後鮮度・スプレッド制御、期待値判定はサンプル蓄積後。
6. **PR6: リスク予算** — 注文数量、全体制限、含み損停止、原子的な注文予約。
7. **PR7以降: 相場ノードとAI比較** — それぞれ独立した比較実験として導入。

最初の提供範囲はPR1〜PR4。コストとAI入力の記録は早期に並行して追加できるが、収益判定への利用は検証基盤が完成してから行う。

## 11. 成果の判定

機能としては再現テスト、会計整合性、将来情報の不使用、既存戦略の移行互換性、アプリ操作への影響を検証する。収益面は未使用期間と前向きペーパー運用で、同資金の比較対象に対する純利益・DD・取引コストの変化を測る。負けた実験も残し、良い結果だけを採用履歴に残さない。

実装着手時の確認事項は、利用可能な履歴期間・板情報、基準PCの性能、ユーザーが許容するDDと資金制約。これらが未確定でもPR1〜PR3の設計・実装は進められる。
